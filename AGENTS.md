# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `proto/` is the only hand-edited code; everything under `packages/typescript/src` and `packages/python/tesla_protocol/*/` is generated. Regenerate with `pnpm install && pnpm generate`; CI fails on any diff, so never edit generated files directly.
- Provenance rules (upstream-tracked vs Teslemetry source-of-record, `TESLEMETRY-EXT` markers, upstream-wins-names policy) live in `PROVENANCE.md`. The enforcement tool is `scripts/upstream_coverage.py`; run it in `--mode pinned` before pushing proto changes.
- Release model: Changesets tracks only the npm package; `scripts/sync-python-version.mjs` copies the version into `pyproject.toml` during `pnpm run version`. Bump rules are in `.changeset/README.md`. Never use changesets prerelease mode (breaks PEP 440).
- `publish.yml` calls `ci.yml` as a reusable workflow (`uses: ./.github/workflows/ci.yml`) so the full CI suite runs against the exact SHA it publishes; both the npm release job and the PyPI job depend on that gate, so keep them both wired to it if you touch the release path.
- The `production` GitHub environment (used by both the npm `release` and `publish-pypi` jobs) has a required reviewer and a branch policy limited to `main` configured directly on the environment - this isn't visible in-repo, only via `gh api repos/Teslemetry/tesla-protocol/environments/production`. Recovery/idempotency behavior for an interrupted publish is documented in the README's Releases section - re-running a failed job is always the recovery path, never a manual registry fix.
- Sharp edge: protoletariat is installed with `pip --no-deps` (see `scripts/generate.sh`) because it over-pins `protobuf<6` while only parsing descriptor sets; its `--exclude-imports-glob` patterns match dependency names WITHOUT the `.proto` suffix.
- The codegen toolchain is fully pinned (`scripts/requirements.txt`, ts-proto in root `package.json`). Changing any pin changes generated output and is a coordinated, changeset-worthy change.
- `CarServer.Response.response_msg` (`proto/command/car_server.proto`) must have every field either modelled in the oneof or `reserved` with a reason comment; `scripts/check_reply_coverage.py` (run in CI) enforces this against its known-field set. Before adding a new reply oneof field, check whether its payload type pulls in an app-only namespace - either model it or add it to `KNOWN_REPLY_FIELDS` as a reserved entry.
- Un-reserving a field to model it trips buf's `RESERVED_MESSAGE_NO_DELETE` breaking check even though it's a wire-compatible addition; `buf.yaml` excepts that rule repo-wide.
- The committed `proto/command/` baseline reflects one specific Tesla app build reconstructed via cross-version protobuf diffing (see `TESLEMETRY-EXT` markers) - check the current `.proto` files for the exact field/tag before assuming a candidate field needs adding.
- `proto/charging/` is a documented exception to the "app-only namespaces are not published" policy (`PROVENANCE.md`): it has no BLE or Fleet API wire path, but is published because it describes the vehicle-charging product domain. Any future app-only module wanting the same exception must be argued explicitly, not assumed from this precedent.
- Adding a wholly new proto directory (a source with no upstream) needs registering in three places: the `buf.yaml` module list, `GROUPS_LIST` in `scripts/generate.sh`, and the layout table + provenance table in `README.md`/`PROVENANCE.md`. TypeScript/Python package exports are wildcarded, so no per-group registration is needed there.
- `scripts/build_catalog.py` regenerates the descriptor-based protobuf surface catalog (`catalog/catalog.json` + `catalog/SUMMARY.md`) from `proto/`: every group, file, package, message, enum, field/tag/type, oneof, reservation, import, and generated TS/Python target. CI fails on any diff or on inconsistent group registration across `buf.yaml`/`GROUPS_LIST`/README, so run it after any proto or group-registration change. `energy_device/google/rpc/status.proto` is catalogued but excluded from message/enum/field totals since it's never a compiled top-level input (only reachable via import).
- `proto/energy_device/`'s field-level content comes from the app's compiled Hermes JS bundle (ts-proto/protobuf.js output), not the DEX - a DEX-only pass sees only the routing enum, not payload types. Each service's top-level oneof envelope (e.g. `TEGMessages`, `WCMessages`) carries the authoritative field-number-to-message map and is the fastest way to cross-check a field's real tag before trusting a `.proto` guess. Some `energy_device.v1` services (`SMAPI`, `WMSAAPI`) appear only as bare names in the bundle with no reachable field-level code, so their request/response bodies aren't recoverable from this artifact. A few `energy_device.v1` messages carry a field whose type lives in a sibling, not-yet-published package (`energy_registration.v1`) - left unmodeled with a short inline comment rather than guessed at or vendored in.
- `buf breaking`'s tag-renumbering forbidding (see `.changeset/README.md`) is a hard CI gate, not a guideline: it fires even when you have hard evidence an already-published field's tag is wrong. Don't renumber a published tag to fix it, no matter how confident the evidence - revert and flag it for a maintainer decision instead.
